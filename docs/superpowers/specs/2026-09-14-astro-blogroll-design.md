## 1. 目标与已确认方向

将早期 Python 聚合脚本重构为 **Astro + TypeScript 静态网站**。采集、数据处理、页面和测试使用一套 Node.js 工具链；GitHub Actions 负责定时更新与构建，GitHub Pages 继续负责托管。

用户已确认：

- 可以替换 Python，重构整个工程结构与行为实现。
- 不迁移旧文章或旧格式；新站今后收录的文章保留历史，同一文章再次出现时更新；订阅源故障或文章不在当前 Feed 中，不自动删除历史。
- 撤回文章由维护者明确处理。
- 接受以文章动态为核心、博客目录为辅助的页面示意，包含文章动态、博客目录、加入我们三个页面。

本设计新增的工程细节见第 4–8 节，采用明确默认值，供本次整体审阅。首版不新增账号、后台服务、数据库、评论系统、全文转载或词云功能。

## 2. 页面与交互

### 文章动态

- 延续示意中的浅蓝与中性色、适度留白、文章卡片、桌面博客侧栏；适配系统深浅主题。
- 顶部保留品牌和三个页面入口。移动端导航换行，辅助侧栏收起，通过博客目录入口访问同样信息。
- 文章卡片显示标题、所属博客、真实日期、纯文本短摘要与原文链接。外链采用新标签页并设置适当的 rel 属性。
- 默认按第 4 节规则排序，每页 20 条。基础文章列表与分页由 Astro 预生成，关闭 JavaScript 仍可阅读和翻页。
- 搜索标题、摘要、文章作者及所属博客名称；可按博客筛选。结果来自全站静态文章索引，不仅搜索当前页。
- 搜索与筛选可以组合；改变条件后回到结果第一页。显示总匹配数、当前分页范围；支持空结果提示与清除条件。
- 搜索结果为浏览器端交互，范围仅为已保存的元数据与摘要，不宣称原文全文搜索。复杂分词引擎不进入首版。
- 搜索或筛选启用时使用首页下的查询参数保存条件及页码；普通浏览使用真实静态分页路径。刷新和分享地址应恢复同一结果，不依赖服务端路由重写。

### 博客目录

- 显示名称、主页、可选介绍、已收录文章数及最近已知文章日期。
- 日期未知或没有文章时显示真实空状态。未知不等于订阅源故障。
- 介绍使用源配置中的内容，不自动编造。无头像时使用名称首字或首字母。

### 加入我们

- 说明准备博客名称、主页、RSS/Atom 地址，使用 GitHub Issue 或 Pull Request 提交，由维护者审核。
- 提供对应 Issue 模板和贡献说明。网页只链接 GitHub 申请入口，不在 Pages 中实现表单接收服务或自动审批。

共通要求：语义化 HTML、可见键盘焦点、明确控件标签；320px 宽度无横向溢出；中文长标题和 URL 可换行；页面标题、描述、站点语言与 canonical 使用统一站点配置生成。

## 3. 工程结构与模块职责

```text
config/
  site.json                 站点名称、说明、公开地址与 base path
  sources.json              博客来源及 enabled 状态
  exclusions.json           文章撤回与来源排除规则
data/feeds/                 按来源保存的规范化文章数据
src/lib/feeds/              请求、解析、规范化、合并实现
src/lib/catalog/            共享数据校验、撤回过滤、日期与排序规则
src/lib/types.ts           共享数据接口（通过目录加载器直接接入页面）
src/pages/                 首页、静态分页、博客目录、加入页面
src/components/            卡片、导航、筛选等组件
src/styles/                设计变量及响应式样式
public/                    要公开的静态资源
scripts/                   刷新、数据和发布产物检查入口
tests/fixtures/            RSS/Atom 与异常样本
.github/workflows/         PR 校验与 Pages 工作流
dist/                      构建输出；不提交源码分支
```

模块接口保持简单：

1. 采集模块接受源配置、旧数据和请求依赖，返回候选文章、逐源结果与诊断。纯解析和合并函数不自动联网或写文件。
2. 目录模块校验数据、应用人工排除规则，提供一致的文章列表和排序结果；页面、搜索索引共享这些规则。
3. Astro 页面只读取已通过校验的数据，不在组件内请求外部博客。
4. 命令入口负责文件读写与退出状态；工作流负责权限、版本关联、并发和部署。

使用项目统一依赖锁文件。Astro 使用静态输出；不配置依赖常驻服务器的功能。RSS/Atom 首先评估 rss-parser，通过来源样本测试后固定稳定版本；若样本证明存在无法接受的字段损失，再在采集模块内部替换解析器。

## 4. 来源、文章与日期模型

### 来源配置

每个来源包含稳定 `id`、`name`、`siteUrl`、`feedUrl`、`enabled`，以及可选 `description`。ID 使用唯一且稳定的 ASCII 标识，不随博客改名改变。页面显示博客归属，独立保留 Feed 提供的文章作者字段；作者缺失时使用来源名称兜底。

`enabled: false` 表示暂停抓取，已收录历史仍展示，目录标注暂停更新。彻底下架来源使用排除规则，不将“暂停抓取”与“下架内容”混为一谈。

### 文章记录

保留 `id`、`sourceId`、`url`、`title`、`summary`、可选 `author`、`published`、`updated`，以及用于匹配的可选原始 GUID。数据文件带 schema 版本；文件不受支持或损坏时使校验失败，不能静默按空数据处理。

- URL 只接受 HTTP/HTTPS，移除 fragment，保留查询参数和路径大小写；避免错误合并实际不同文章。
- 首次标识以来源 ID 和规范化原文链接生成；优先按同来源 URL 匹配，可靠 GUID 用于链接变化时保持旧标识。无法唯一匹配的情况保留诊断，不能随意覆盖另一篇文章。
- 同一文章更新非空、有效字段；暂时缺失或无效的字段不擦除已有有效值。明确清空由人工处理规则完成。
- 摘要为纯文本。保留来源提供的摘要文本用于搜索，卡片展示时截取约 160 个 Unicode 字符；不主动访问文章页面抓取全文。
- 模板与浏览器搜索结果均按文本渲染外部字段，禁止将标题或摘要直接拼成 HTML。

### 日期与排序

日期采用可空的显式结构，保留原始值，并区分 `instant`（含明确时区的时刻）、`date`（仅日期）、`local`（没有时区的日期时间）。无法解析的值作为未知，原始内容保留在诊断记录中。

- `instant` 保存标准时刻，页面按 Asia/Shanghai 展示日期；`date` 按原日历日期展示；`local` 显示原日历日期，保留原值但不假设时区。
- 文章“修改日期”只来自真实 updated，“发表日期”只来自真实 published；不把抓取时间写入这两个字段。
- 排序选择有效 updated，否则选择有效 published。先按上述显示日期降序；同日中有明确时刻的记录按时刻降序，其后放仅日期或无时区记录；最终以稳定文章 ID 升序打破相同排序键。
- 两个日期都没有的文章置后，按稳定 ID 排序。缺失日期本身不是丢弃文章的理由。

该排序明确改变旧站只按 updated 字符串排序的行为。

## 5. 历史、暂停与撤回

第一版保留全部已收录的文章元数据与摘要，不按年龄自动淘汰。网站不下载完整历史正文或媒体，也不承诺恢复 Feed 从未提供的内容。

`exclusions.json` 保存人工撤回记录，支持按文章 ID、同来源已知 GUID/原文 URL 别名，或整个来源 ID 排除。撤回记录独立于采集结果长期保留，不在刷新时自动清除；恢复收录需明确移除对应规则。若同一内容同时更换 GUID 和 URL，首版不承诺自动识别，需要维护者补充别名。

实现使用快照中的可选 `tombstones` 保留被撤回文章的身份别名（ID、URL、GUID，不含标题或摘要），让后续刷新也能识别改链接的记录。这些身份不进入公开目录和搜索数据。删除对应排除规则后，当前 Feed 可重新收录内容。

- 在候选数据合并和页面/搜索索引读取时都应用排除规则。
- 已撤回文章即使再次出现在 Feed 中，也不能重新收录或出现在搜索结果中。
- 来源暂时失败、暂停抓取、从 Feed 中消失，与人工下架是不同状态。
- 维护者通过配置提交执行撤回；本轮不提供管理后台。源码 Git 历史中的既有数据不通过重写历史清除，撤回指当前数据和站点不再展示。

## 6. 抓取与失败恢复

- 默认每天北京时间 00:30 刷新，保留手动刷新入口；时间可配置，但不承诺 Actions 精确到点执行。
- 并发数上限默认 4。单次请求超时 15 秒，每个源最多 2 次请求；网络失败、408、429 和 5xx 可有限重试，普通 4xx 不反复请求。响应体上限默认 5 MiB，防止异常响应无限占用资源。
- 只对收到的响应解析一次，规范化后与该来源旧数据合并。单条损坏记录跳过并计入诊断，不清空其余有效文章。
- 网络失败、无法解析、零条有效文章记为来源异常，保留该来源已有数据；新来源无数据时可以暂时仅出现在目录并标记无文章，不伪造内容。
- 部分源成功时，成功源更新、失败源沿用旧数据；发布可用站点，并在运行摘要及本次静态状态数据中记录降级。
- 所有启用源均失败，或未取得任何有效文章时，刷新任务失败，不更新持久数据、不部署。本条不阻止后续使用现有有效数据发布代码修复。
- 候选数据、网页和资源检查通过后，才进入数据保存及部署流程。失败快照不得覆盖上一次有效数据。

运行报告区分成功、部分降级、失败。文章日期、快照内容变更时间、实际来源检查时间分别记录；不能互相冒充。

## 7. 数据保存与 GitHub Pages 发布

### 事件与权限

- PR：离线校验、测试、构建、检查产物。使用固定样本和仓库数据；不获取写入或部署权限，不执行真实采集。
- 受信任默认分支上的代码 push：使用仓库已有有效数据构建并部署，不强制抓取 RSS。
- schedule / 手动刷新：读取旧数据、抓取并合并、校验和构建，然后保存数据及部署。默认分支名称在实施时从真实仓库配置核实，不能仅凭本地 master 名称推断。
- 手动流程另提供“仅重建”方式，用于部署重试或离线数据重建。

构建测试 job 只读；仅保存数据的 job 使用 `contents: write`；部署 job 使用 Pages 所需权限。PR 不进入后两类 job。

### 持久化与并发

- 在默认分支 `data/feeds/` 保存有效数据，按规范化业务内容变化才提交。仅允许明确列出的数据 JSON 文件写入，不使用 `git add .`，不提交 dist、生成 HTML 或时间戳噪音。
- 发布流程之间共用并发组，禁止旧运行覆盖较新部署。默认分支前进时，基于旧版本的流程终止或从新基线重建，不能强推。
- 使用稳定哈希作为 dataVersion，并记录源码 SHA，把构建所用数据与本次产物关联。快照代表验证通过的数据，部署成功另由 Pages job 结果证明。
- 使用 GITHUB_TOKEN 写回数据后，在当前工作流继续部署，不等待写回提交触发另一轮 push 工作流。
- 如果保存数据失败则不发布该候选版本。若数据已保存而部署失败，保留明确失败状态，可通过“仅重建”重试已有有效版本。
- 若分支保护阻止数据自动写入，保留检查和构建能力，报告具体阻碍；不自动放宽保护规则。独立数据分支是后续可选择的兼容方案，不隐式切换。

实际来源检查时间仅属于执行过刷新的一轮：写入本次产物状态 JSON 与 Actions 摘要。代码 push / 仅重建不虚构新检查时间，状态标识为本轮未检查；页面可显示持久数据的内容变更时间，但不把它标成最近连通性检查。

### 发布产物

- 使用 GitHub 官方 Pages artifact 部署链路，只上传 `dist/`。Pages 本身只提供静态文件。
- base path 集中处理；项目地址场景使用 `/BaiyunUBlogroll/`，自定义域名根路径场景使用 `/`。资源、分页、搜索索引、导航与 canonical 同时验证。
- 部署产物不包含 Python 脚本、测试、内部配置、备份、词云字体或开发依赖。所有公开数据必须经过与页面相同的撤回过滤。
- 维护说明写明 schedule 可能延迟和公开仓库无活动停用后的恢复办法；cache 和临时 artifact 不作为文章历史的唯一存储。

官方约束与来源链接见调研文档；真实 Pages 设置、分支保护和来源连通性在实施阶段核实。

## 8. 全新重建与验收

用户明确不迁移旧数据、弃用旧站。新版本仅保留四个博客作为初始来源配置，从当前 RSS/Atom 重新收录；不导入旧 config.json 的 107 条记录，不提供旧格式兼容层。

1. 原工作区修改已备份至忽略的 `.local/legacy-before-rebuild`，仅用于保护本地编辑，新站不读取备份。
2. 在 `codex/astro-pages-rebuild` 分支实现数据模型、采集、离线构建与已确认页面，随后退役旧 Python 链路和无用资产。
3. 完成桌面、窄屏、键盘和无 JavaScript 阅读验证，更新维护说明及加入模板。

| 验收项 | 通过条件 |
| --- | --- |
| 全新收录 | 不依赖旧 config.json；缺少历史快照时可构建空站；从当前 Feed 重新获取真实文章 |

| 历史与撤回 | Feed 缩短仍保留历史；人工撤回后重复抓取、离线构建与搜索都不使其复现 |

| 失败恢复 | 部分失败保留有效站点；全部失败不覆盖数据或部署；异常空源不清空历史 |

| 状态 | 实际检查时间、内容变更、构建和部署结果清楚分离 |

本表为后续验收标准，不代表当前已完成检查或测试通过。实施按已确认方向推进；线上发布仍以实际部署结果为准。
